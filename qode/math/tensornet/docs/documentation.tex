		\section{Quick Start}

	\subsection{Installation}

\texttt{Qode} can be obtained from \url{https://github.com/adutoi/Qode}.
If you have this file, you probably already did that.  Next, set your python path.
In a \texttt{bash} terminal:
\begin{lstlisting}
% export PYTHONPATH=$PYTHONPATH:<.../path/to/Qode>
\end{lstlisting}
where \texttt{<.../path/to/Qode>} is replaced by the path to the cloned packaged directory
(named \texttt{Qode/}, unless you changed it, and which should have \texttt{qode/} as a subdirectory).
You then import the \texttt{TensorNet} subpackage of \texttt{Qode} into your python code via
\begin{lstlisting}
from qode.math import tensornet
\end{lstlisting}
or by importing selected identifiers, as done in the examples below.
\texttt{TensorNet} works at least with \texttt{Python 3.12} onward, and probably
 a few earlier version as well.

The minimal third-party requirement for using \texttt{TensorNet} is the intallation
 of some package for handling the backend tensors (most basically. for example, \texttt{NumPy})
 because \texttt{TensorNet} really just defines a high-level, cleanly readable syntax
 for tensor manipulations.
It does none of its own tensor arithmetic.
The most ``heavy lifting'' that it does is the storage of the structures of many
 contracted tensors (a tensor network$^*$), and implementing a heuristic for the optimal contraction
 path for a given network, delegating the contactions to the backend tensor engine.
[$^*$ tensor network: tensors are nodes of a graph and contractions and reductions are ``multipartite edges.''
 See figure in introduction after this Quick Start section.]

If using \texttt{NumPy} or \texttt{TensorLy} (and maybe a few others by the time you read this)
 there are already interface files for the backends that allow for a seamless,
 get-up-and-running experience, but effort has been made to make the construction of a new
 interface file also extremely easy (perhaps as short as 50 lines, or less if the syntax
 is similar enough to standard tensor libraries
 (\texttt{A += B, A[i,j,k,...],} etc.)
 to build off the
 interface base class (which should exist soon after writing this).
Read on for more information.

		\section{More Stuff}

	\subsection{Theory}

Our goal is to evaluate expressions of the following form for the elments
 of tensor $\mathbf{Z}$
\begin{eqnarray}
  \label{horrible_tensor}
  Z_{pqr} = \sum_{stuvwxy} A_{qpst} B_{stuv} C_{uqw} D_{uxryy} E_{wx}
\end{eqnarray}
This is probably not a realistic form for any practical problem,
 but it illustrates a number of features:
Index $v$ is summed but occurs only once, whereas index $u$ is shared
 between three tensors, index $y$ is trace-like on one tensor only,
 and one of the uncontracted (free) indices occurs twice on the right-hand side;
 the others are more ``normal,'' but, at that, $\mathbf{A}$ and $\mathbf{B}$
 are connected by two such indices.
For lack of a better word, we will call the multiple appearance of free indices
 a ``reduction'', as it reduces the number of tensor axes, and a subsequent
 sum over it would be a contraction.

\begin{figure}[!htb]

  \end{center}
  \vspace{-1.5cm}

     tensor network, represented as a hypergraph.
    Evaluation of sub-graphs proceeds down the page until explicit evaluation is complete.
    The algrebraic definitions of the sub-graphs used are also given.
    The evaluation flow is purely hypothetical, only to illustrate the kinds of steps that can

The structure of the right-hand side of Eq.~\ref{horrible_tensor} can be represented
 as a hypergraph, as shown in Fig.~\ref{tensor_network_graph}, 
 where the nodes are the tensors, and the hyperedges are the summations
 over indices (henceforth, just ``graph'' and ``edges'').
The index positions of the associated tensors that are connected can be thought
 of as a properties of the edges (\textit{e.g.}, there is an edge that connects
 the 3rd index of $\mathbf{A}$ to the 1st index of $\mathbf{B}$, where counting
 in this representation starts at 1).
The free indices are thought of as simply being properties of the nodes that
 are not technically part of the graph.
Nevertheless, we have a special notation to keep track of these.
The ordering of thefree indices in the product is given by 
 circled numbers connecting to the corresponding index positions of the inputs.
Should we have an index that is simply summed, we just draw a line from its
 position to a sum sign, but a dummy vector could formally be introduced as a node here.
An important feature is that the graphs need no index ``letters'' for their description;
 only non-arbitrary identifiers are necessary to internally represent a tensor network,
 once it is resolved from the user input via the front end syntax.

Given a fully resolved network, it will eventually be required to resolve it.
The sequence given in Fig.~\ref{tensor_network_graph} is not meant to be optimal.
It is meant to illustrate the kinds of steps that can be taken.
\texttt{TensorNet} does contain a heuristic to try to identify the most likely optimal
 path, and it works very well in simple situations.
More importantly however, this heuristic is separable from the rest of the
 code (under a couple of assumptions addressed later).
Swapping this out (and providing an interface to any options) would be a developer task,
 as opposed to a user task (such as providing an interface to the backend is a user task), 
 but it should be pretty straightforward to make use of more advanced algorithms as long
 as the storage paradigms for the network information is translatable.
For purposes of illustration, however, we will comment that the first steps are 
 obviously correct.
The first step is obviously correct, however.
For what can only result in future reduction of arithmetic and memory usage, $\mathbf{D}$
 can be contracted to a smaller quantity without changing structure.
Similarly, though it does not result in any reduction of problem size, the structure of
 the diagram can be simplified by considering the two contractions connecting $\mathbf{A}$
 and $\mathbf{B}$ to run over a single super-index;
 it is clearly most efficient to perform those contractions in a single step, when appropriate.
Note that if the diagram had not contained a loop structure, the contraction over the
 triply shared index could have been done in a single step.

Regardless of the actual contraction path decided upon, or even how it is decided upon
 (using the heuristic as of the time of writing, or something more advanced that is patched in),
 once the sequence of steps is determined, \texttt{TensorNet} delegates a series of 
 tensor contractions to the backend engine.
The quantities received by the backend are always of its native type.
Under the most normal circumstances (no hyperedges), it will recieve two at a time,
 along with information about what indices to contract.

tensors when ``appropriate'' or find some way to force the issue in the background.
What to to if a library does not even have a notion of a 0-dimensional tensor.  I should work from that assumption.

	\subsection{Assumptions About Sub-graph Decomposition}

Here I should expose some assumptions about how graphs are to be evaluated stepwise.
Any heuristic that obeys these assumptions should be straightforwardly swappable with what is
 presently in use.
Any backend that can handle the primitive steps required is usable (and any backend can be
 made useable, read on).

I assume firstly that all of the nodes are explicit tensors that do not consist of sums of other
 tensors (ie, unless those can be, and are, cast as contractions, and are therefore just subgraphs).
What cannot be cast in this form is a sum of tensors where the terms are themselves graphs of
 different structures.
My code enforces this at the top level by turning any networks that contain sums into sums of networks.
The networks are all evaluate first, and the sum is taken at the highest level.
Of course, the user could just evaluate the sum themselves and provide it as a primitive input,
 or stack it and make it look like another tensor, but we don't automatically handle it.

For a given network, we assume
that each step will excute either one contraction group or one reduction group.
A contraction group consists of all contractions of the same structure between the same
 nodes (ie, the only difference is the positions of the indices connected).
A path that does something more complicated than this will require something more 
 substantial than just a translator to use a different heuristic.

With respect to the backend, the backend should expect then to get such a step as just described.
As long as there are no hyperedges (everything is a true edge), then it will never get more than
two explicit tensors at a time, though it may be asked to contract more than one index at a time.
The latter capability is ubiquitous, and the widely available einsum will handle the former as well.
However, if the backend can really only do two tensors at a time, the user will have to implement
the arithmetic to turn a contraction of three tensors into two contractions of two tensors
(for example).

	\subsection{Original introduction to \texttt{tensors.py}}

We have 4 different types of top-level tensors \\
  \texttt{contraction\_expression} \\
  \texttt{tensor\_sum} \\
  \texttt{tensor\_network} \\
  \texttt{primitive\_tensor} \\
All of these are built off of \texttt{tensor\_base}.  The latter three are built off of \texttt{resolved\_tensor} (which
is based on \texttt{tensor\_base}) indicating that they are completely well-formed.

\texttt{contraction\_expression}
behaves like a tensor so long as it is well formed, but it could be incomplete.  The basic problem
is that, when connecting a bunch of tensors with @, it is not possible to automatically discern
when the string is finished (ie, when all intended target free indices are present).  Only the user can decide
when to "close" the string, but we don't want to make the user do this explicitly.  Therefore,
we allow this incomplete class, whose *resolution* is a \texttt{tensor\_network} (it always resolves to a
\texttt{tensor\_network}). This is triggered by taking another action on it that is not @ or *.  A \texttt{tensor\_sum}
can only contain types \texttt{primitive\_tensor} and \texttt{tensor\_network}.  An attempt to include another
\texttt{tensor\_sum} will cause it to be expanded out as a single sum (and \texttt{contraction\_expression} will 
be automatically resolved to \texttt{tensor\_network}).  A \texttt{tensor\_network} can only contain
type \texttt{primitive\_tensor}, and including one network (or \texttt{contraction\_expression}) into another network causes explicit expansion
into a single network.  Taking this together, this means that a \texttt{tensor\_network} cannot contain a 
\texttt{tensor\_sum}.  An attempt to put a \texttt{tensor\_sum} into a \texttt{tensor\_network} will result in the hierarchy
being swapped to a sum of networks.  The reason for this is purely practical.  At the moment,
I cannot think of a way of finding the best path to evaluate a network that contains sums.

	\subsection{Original introduction to \texttt{tensor\_network} in \texttt{tensors.py}}

Barebones theory (written much later after a forensic debug battle).  A \texttt{tensor\_network} object contains
two fundamental pieces of information (and other incidental info).  One is a list of contractions.
Each contraction itself is a list of two-tuples; each two-tuple identifies a tensor and the index
of that tensor involved in the contraction.  So if a contraction contains two two-tuples, then 
two indices are contracted with one another, but there might be more for unusual contractions.
The ordering of the list of contractions is irrelevant, as is the ordering of the list of two-tuples
that defines a given contraction. The other piece of information is a list of free indices of the result,
which correspond to uncontracted indices of the tensors in the network.  This list is ordered, and each
free index is itself a list of two-tuples with the same tensor-index structure as the two-tuples that
define a contraction.  In the most usual case, each such list corresponding to a free index will be of
length one, but if there is more than one tensor index that corresponds to a single free index it is because
those indices are set equal to each other and reduced to a single free index.


	\subsection{Original introduction to \texttt{primitive\_tensor\_factory} in \texttt{\_\_init\_\_.py}}

Philosopy:  A backend (in the sense of the value of the argument backend below) is a class that
contains static methods that perform basic operations on objects that represent tensors of a specific
type. These will henceforth be called backend tensors.  Tensornet then uses the backend functions to
manipulate the backend tensors according to what is encoded by its high-level syntax.  Objects of the
class defined below are factories for the primitive tensornet tensors which each wrap a backend tensor
(and never modifies it).  An important point is that a given backend can have multiple factories
depending on how what a user is doing.

The creation of a tensornet primitive tensor should only take place via a factory (which is why
that class name is "hidden" here with the underscore convention) because this is the mechanism by
which a backend tensor is associated with its backend functions and the utility for contraction creation.
In the most basic case, this creation is done by the .init() method (not \texttt{.\_\_init\_\_}, which creates the 
factory).  The method .zeros() is a convenience function for creation of a tensornet primitive storing
a new backend tensor (via a backend method) so the user need not create such a zero tensor first and
then "wrap" it (\texttt{.scalar\_tensor()} is similar and was added for completion, but commenting it out essentially
documents that we have not yet found a use case ... the necessity for the backend to be able to create
such a thing however has to do with obeying expectations about type uniformity).

Finally we come to the arguments \texttt{data\_wrap} and \texttt{data\_unwrap}, the method .data(), and the idea of multiple
factories for the same backend.  It is important that tensornet works only with a notion of backend
tensors and the functions it is given for them without knowing anything further about their properties.
But the user may be working with some abstracted backend tensors.  Although they contain, or
somehow represent the existence of, a specific concrete tensor (eg, numpy, tensorly, pytorch), they 
do not have the usual expected behavior (e.g., [] might not even get an element).  We will call such 
things meta tensors, it might be very inconvenient for the user to make their in-house meta tensor behave 
exactly like a concrete tensor, right down to letting a numpy.ndarray (etc) be instantiated from it.  It
will also be very inconvenient if the user has to always use the unbound function raw() and then afterward
extract the concrete data for cooperation with other linear algebra libraries.  The converse is also true
that it will be annoyingly repetitive to always create the meta tensor from a concrete tensor from elsewhere,
and then pass that to the factory.  So, therefore, a factory can be created that takes the functions
\texttt{data\_wrap} and \texttt{data\_unwrap}.  Although their actions are not constrained as such, the idea is that \texttt{data\_wrap}
is a function that takes a concrete tensor and returns an object of the meta tensor type with which
backend works, and \texttt{data\_unwrap} does the opposite, extracting and returning (by reference) the concrete
tensor represented (eg, contained within) the meta tensor.  The convenience function .data() called
on a tensornet tensor causes evaluation of the (potential?) network (sum?) and returns directly the concrete
tensor associated with the result.  By default, \texttt{data\_wrap} and \texttt{data\_unwrap} are just pass-throughs,
which means that .data() is just an alias for the unbound function raw(), which forces evaluation and
returns a backend tensor (which is typically already a concrete tensor type).  Since this automatic
wrapping and unwrapping might not always be the desired behavior, more than one factory can be defined,
per need.

Addendum 1:  There is no requirement that a meta tensor is not itself also a concrete type, and that
this concrete type might be initialized from multiple other concrete types, which might not even be
different than its own type.  So if we interpret the concrete and meta layers to both be tensorly,
where the meta layer can be initialized also from numpy or pytorch (etc), then there it is a perfectly
clean for the user to provide as \texttt{data\_wrap} a function that makes a tensorly tensor from some input
which may or may not be of tensorly type), and to leave \texttt{data\_unwrap} as the default pass-through.

Addendum2:  One question that can be asked about the design is: why am I giving in a separated
backend with functions that perform manipulations on a tensor, rather than just insisting that backend
tensors have certain properties, like += (which would also make the insides of tensornet prettier).
The answer is that one might have enough serious work to do in the abstracted/meta backend already,
without having to define yet more operations that make the thing look almost like a tensor, but not
completely.  One can imagine various inheritance and virtual method schemes, but one is always going
to end up in one of two places: 1. Forcing the user to make a new class for their backend tensors
(and then maybe always, even when using "normal" tensors), or 2. automating the creation of the 
backend tensors with the expected operators in terms of some other/divorced set of instructions.
In case 2, we are back where we started from the user point of view, though the insides of tensornet
look nicer (for the price of another file/class and layer of abstraction).

Addendum 3: The \texttt{.\_\_init\_\_()} method used to take a \texttt{copy\_data} argument which meant that the factory should
copy the provided primitive before storing it as an argument for further use.  Probably unusual, but
a user might do this if they intended on modifying that primitive for some other use while it was still
in use by the tensornet code (you never know ...).  This can now be done by the user with the \texttt{data\_wrap}
option.

	\subsection{Questions about using \texttt{opt\_einsum}}

\url{https://joss.theoj.org/papers/10.21105/joss.00753}

Clearly there are advantages to the fact that the authors of \texttt{opt\_einsum} have given much more
thought to their heuristics, but it is not immediately available for all backends, and the
fact that my heuristics live above the backend and need to know nothing about the hardware
to at least make a *good* guess (maybe not the best) still makes it useful.  That said,

I'm not a big fan of how this works because, IMO, all decisions about how to contract tensors should
be as local as possible.  Say, for example, you wanted to merge two codes that had been using different
backends for the tensors.  It will be a lot more convenient if you don't have to force them to agree on one.
This is why my tensors carry knowledge of their backends with them, and the only thing that matters when
two tensors meet is that they are the same (which is presumably the case within any given code domain).
Now there is this wart, where you insist that all tensors (even those with different backends) are either
going to use the frontend or the backend contraction path.  Probably this is ok for well over 90% of use
cases, but I would like to clean it up.  At the same time though, making the \texttt{backend\_contract\_path}
option a feature of a backend is also not really (ie, could carry this option around with the tensors)
because it is not a feature of the backend, it is a feature of a contraction within the context of a 
backend.  We certainly do not want to insist that a tensor created with one way of determining the contraction
path cannot be contracted with a tensor with a different "opinion" on the way of determining the contraction
path.  At the moment then, this is the least of evils.  At least a user can dynamically switch back and forth.

Actually the obvious solution is between the extremes.  Similar to timings, the interface class
contains a function that can modify a module-level variable.  So tensors with the same backend will
all behave the same way, and this runtime distinction does not define a backend, but different backends
can still behave differently (and you could have two nominally different backends if you want that 
still can communicate via raw tensors)
